Goal and outcome
- Goal: Implement event-driven orchestration hooks and an idempotent queued job system with debounce and anti-thrash behavior, using existing persistence structures.
- Outcome: Added a hook dispatcher and durable orchestration job queue backed by the existing `events` table, integrated event->hook->job dispatching, moved queue/orchestration workers onto idempotent jobs, and added integration tests proving dedupe, debounce/coalescing, and restart safety.

Key code changes
- Added hook dispatcher:
  - `server/src/services/orchestration/hooks.ts`
  - Implements hooks: `on_node_created`, `on_child_attached`, `on_dependency_added`, `on_status_changed`, `on_node_output_updated`, `on_merge_completed`, `on_merge_failed`, `on_timer_tick`.
  - Maps domain events to orchestration jobs with deterministic idempotency keys and per-hook debounce/dedupe behavior.

- Added orchestration job queue worker:
  - `server/src/services/orchestration/jobQueue.ts`
  - Persists pending/completed job evidence in `events` payloads (`orchestration.job.pending` / `orchestration.job.completed`), with no new primitive tables.
  - Supports job handler registration, idempotent enqueue, debounce delay (`notBefore`), dedupe windows, restart-safe processing, and periodic timer-tick anti-thrash scheduling.
  - Deletes pending rows after completion markers are persisted to prevent starvation from historical pending rows.

- Integrated hooks into event recording:
  - `server/src/services/events.ts`
  - `recordEvent` now derives orchestration jobs from inserted events and enqueues them immediately.
  - Added optional event id input and return value `{ eventId, inserted }`.

- Migrated workers to queue-driven orchestration jobs:
  - `server/src/services/queue.ts`
    - Registers `task_queue_dispatch` handler.
    - `kickTaskQueueProcessing()` now enqueues per-project idempotent jobs instead of running inline polling loops.
  - `server/src/services/planOrchestrator.ts`
    - Registers `plan_orchestration_pass` handler.
    - `kickPlanOrchestrationProcessing()` now enqueues per-project idempotent jobs.
  - `server/src/index.ts`
    - Starts orchestration job queue worker at boot.

- Added unified status-change hook trigger event:
  - `server/src/application/cliServices.ts`
  - `server/src/services/runtime.ts`
  - Both now emit `task.status_changed` events on status transitions so hook dispatch is consistent across CLI/runtime mutation paths.

- Added integration coverage:
  - `server/src/integration.test.ts`
  - New tests validate:
    - duplicate hook events do not create duplicate effective work,
    - burst updates are debounced/coalesced,
    - queue survives worker “restart” without reprocessing completed work.

Remaining risks or follow-ups
- Hook mapping currently relies on existing event taxonomy; if new event types are introduced without mapping updates in `hooks.ts`, orchestration reactions may be incomplete.
- Completed-job evidence is durable, but long-term retention in `events` may need pruning/archival policy to avoid unbounded growth.
- Some non-CLI/non-runtime write paths may still require audit to ensure every meaningful status/output transition emits the canonical hook-driving event types.
- Debounce/dedupe constants are currently fixed values; tuning may be needed under production load characteristics.
