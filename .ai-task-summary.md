## Goal and outcome
- Goal: Implement deterministic workflow checks for `file_created`, `file_exists`, `file_modified_within`, `line_present_in_file`, `json_path_equals`, `command_exit_code`, `stage_complete`, `node_merged`, and `child_nodes_created_count`.
- Outcome: Added a deterministic check runner that evaluates all nine check types and persists one `workflow_check_results` row per check per stage run. Added tests validating deterministic pass/fail behavior and stage-run persistence.

## Key code changes
- Added deterministic workflow check service:
  - `server/src/services/workflowChecks.ts`
  - New types:
    - `DeterministicWorkflowCheck`
    - `CheckComparator`
    - `EvaluatedWorkflowCheck`
    - `RunDeterministicChecksResult`
  - New entrypoint:
    - `runDeterministicChecksForStageRun(...)`
  - Behavior implemented:
    - Evaluates all required check types.
    - Persists results via `createWorkflowCheckResult(...)` in `workflow_check_results`.
    - Replaces prior stage-run check rows before writing a fresh deterministic snapshot.
    - Optionally fails a running stage (`transitionWorkflowStageRunStatus(... -> failed)`) when any check fails.

- Added deterministic check tests:
  - `server/src/services/workflowChecks.test.ts`
  - Coverage includes:
    - Per-stage-run check result persistence.
    - Deterministic pass/fail outcomes across file/json/command/stage/node/count checks.
    - Stage failure transition when `failStageOnAnyFailure` is enabled and checks fail.

## Questions answered during this task, including each answer
- Q: Were the required deterministic checks already implemented?
  - A: No. Only persistence tables/repository CRUD existed.

- Q: Where should check results be stored to satisfy acceptance criteria?
  - A: In `workflow_check_results`, keyed by `workflow_stage_run_id`, using existing workflow repository APIs.

- Q: How to ensure deterministic behavior for repeated evaluations?
  - A: Evaluate checks with explicit inputs, serialize comparable values deterministically, and replace prior stage-run check rows with a fresh snapshot per run invocation.

- Q: Should stage status change on check failures?
  - A: Implemented as optional behavior via `failStageOnAnyFailure`; when enabled and stage is `running`, stage transitions to `failed` with failure details.

## Remaining risks or follow-ups
- The deterministic check runner is implemented and tested, but not yet wired into a broader workflow execution orchestrator/route/CLI command in this task.
- `command_exit_code` currently uses local process execution with default timeout; if stricter sandboxing or output limits are required, that policy should be added explicitly.
- JSON path support is intentionally simple dot/index traversal; if JSONPath expression parity is needed, an extended parser should be introduced.
