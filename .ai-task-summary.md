# Task Summary

## Goal and outcome
- Goal: Ensure non-exec start path (API + CLI) triggers runtime AI sessions for decomposition work, keep exec tier start behavior unchanged, and prevent decomposition side effects from node creation alone.
- Outcome: Completed. Non-exec `start` now launches runtime sessions (same startup path used by exec), exec behavior remains intact, and node creation no longer enqueues decomposition/readiness orchestration work.

## Key code changes
- Updated API node-start flow to use runtime session start for all tiers:
  - File: `server/src/routes/tasks.ts`
  - Removed non-exec manual enqueue of `decompose` orchestration jobs.
  - Kept dependency-block checks.
  - Starts runtime via `startTaskRuntimeWorker(...)` for both exec and non-exec.
  - Retained `orchestration.manual_start` audit event for non-exec nodes, now marked with `strategy: "runtime_session"`.
- Updated CLI node-start service flow similarly:
  - File: `server/src/application/cliServices.ts`
  - Removed non-exec manual enqueue of `decompose` jobs.
  - Starts runtime via `startTaskRuntimeWorker(...)` for both exec and non-exec.
  - Retained non-exec manual-start audit event with `strategy: "runtime_session"`.
- Stopped node-creation hooks from triggering decomposition/readiness:
  - File: `server/src/services/orchestration/hooks.ts`
  - `on_node_created` no longer contributes task-scoped readiness job.
  - Removed explicit `decompose` enqueue branch for `on_node_created`.
  - Resulting `task.created`/`plan.created` events now only map to global queue/orchestration-pass jobs.
- Added regression coverage:
  - File: `server/src/services/orchestration/hooks.test.ts`
  - New test asserts `task.created` does not produce a `decompose` job.

## Research performed for this task and key findings
- Code-path tracing (API + CLI start handlers):
  - Found non-exec starts in both API and CLI explicitly enqueued `decompose` jobs instead of starting runtime sessions.
- Runtime startup behavior review:
  - `startTaskRuntime(...)` supports both `execution` and `plan` modes and already builds/runs Codex sessions using generated prompts; no mode restriction prevented non-exec runtime starts.
- Event/hook orchestration review:
  - `task.created` and `plan.created` mapped to `on_node_created`; that hook scheduled both readiness and decomposition, causing creation-time side effects.
- Test surface review:
  - Existing integration tests covered manual start auditing but did not directly assert node-created hook job types; added focused unit test at hook layer.

## Questions answered during this task, including each answer
- Question: Where does non-exec `start` currently route in API and CLI?
  - Answer: It routed to orchestration by enqueueing `decompose` jobs in both `routes/tasks.ts` and `application/cliServices.ts`.
- Question: Can non-exec nodes be started through runtime session code safely?
  - Answer: Yes. `startTaskRuntime` supports plan-mode tasks and starts tmux/Codex sessions with effective prompts.
- Question: Does node creation alone currently trigger decomposition side effects?
  - Answer: Yes. `task.created`/`plan.created` mapped to `on_node_created`, which enqueued readiness and decompose jobs.
- Question: How to preserve exec-tier behavior while changing non-exec behavior?
  - Answer: Use the same runtime start path for all tiers; exec continues unchanged, non-exec aligns to runtime session start.
- Question: Should manual-start audit signals remain?
  - Answer: Yes. They were retained for non-exec starts, with payload updated to reflect runtime strategy.

## Remaining risks or follow-ups
- `on_node_created` still emits global `task_queue_dispatch` and `plan_orchestration_pass` jobs; while decomposition no longer occurs directly from creation, these global jobs may still do other orchestration work by design.
- Manual-start audit payload changed shape (`requestedAutoMode`/`strategy` vs previous `pendingEventId` semantics). If external consumers depend on old payload keys, they should be updated.
- Delta-plan path still performs deterministic child materialization (`delta_<hash>`), which remains separate from this task’s scope.
