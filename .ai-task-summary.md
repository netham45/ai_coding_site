# Task Summary

## Goal and outcome
Goal: Implement the app-vs-project SQLite ownership split per `docs/adr-sqlite-persistence-split.md`.
Outcome: Completed. The codebase now uses `data/app.sqlite` only for global entities (`users`, `user_settings`, `projects`, `project_members`) and per-project DB files at `<project.base_path>/.ai-coding/project.sqlite` for project-local entities (`tasks`, dependencies/transitions/sessions, plan tables, `ide_instances`, `merge_records`, `events`, and project prompt/config fields via `project_config`).

## Key code changes
- Split migration definitions into app DB and project DB schemas in `server/src/db/migrations.ts`.
- Replaced monolithic DB bootstrap with:
  - `appDb` for global tables
  - project DB open/cache/init/validation helpers in `server/src/db/index.ts`
  - metadata validation (`project_metadata.project_id`) and project config ownership (`project_config`).
- Added explicit ownership/integrity invariants in `server/src/db/index.ts` comments:
  - single source of truth per table,
  - no cross-file foreign keys,
  - cross-DB links by IDs only.
- Added cross-DB lookup/context helpers in `server/src/db/ownership.ts`.
- Refactored routes/services/websocket gateways to use correct DB ownership:
  - app DB auth/settings/membership checks in app-level code,
  - project DB for tasks/plans/runtime/events/ide/merge state.
- Updated types in `server/src/types.ts` (`AppProjectRow`, `ProjectConfigRow`, hydrated `ProjectRow`).
- Updated README persistence notes for split ownership and invariants.

## Tests/validation performed
- TypeScript build passed for server:
  - `npm run build -w server`
- Full workspace build passed:
  - `npm run build`
  - includes server compile and web build.

## Remaining risks or follow-ups
- Existing monolithic `app.sqlite` data migration into per-project DBs is not implemented in this change; current behavior is schema/ownership cutover in code.
- Some cross-project task lookup paths currently scan project DBs; this is functionally correct but may need indexing/caching strategy if project count grows.
- Operational handling for project DB corruption/unavailability is implemented at DB open/validation boundaries, but additional admin tooling for repair/restore workflows would improve operability.
