## Goal and outcome
- Goal: Implement cross-tier dependency support so any node can depend on any other node, enforce DAG validity with cycle prevention, and expose blocker diagnostics including reasons and lineage.
- Outcome: Added a shared orchestration dependency graph validator and diagnostics utility, wired it through CLI and API task/plan flows, persisted/queryable dependency reasons in node metadata, and added diagnostics surfacing for unresolved dependency IDs + reasons. Integration coverage was updated and all tests pass.

## Key code changes
- Added tier-agnostic dependency graph utility:
  - `server/src/services/orchestration/dependencyGraph.ts`
  - New capabilities:
    - Dependency normalization across tiers (`epoch|phase|plan|task|exec`)
    - Existing+proposed graph assembly
    - Deterministic cycle detection with actionable cycle path messages
    - Validation helpers for single-node creation and plan batch materialization
    - Dependency diagnostics builder (unresolved refs + lineage edges)
- Extended metadata utility to persist same-tier dependency refs (including reasons):
  - `server/src/services/orchestration/metadata.ts`
  - `buildInitialNodeMetadata` now accepts `sameTierDependencies` and `crossTierDependencies`.
- Refactored CLI dependency handling to use graph validation and persist reasons:
  - `server/src/application/cliServices.ts`
  - Removed duplicated task-only resolver logic.
  - `createTask` now validates `dependencyTaskIds` + `dependencyNodeRefs` via shared graph utility.
  - Plan approval flow now validates proposed node graph rather than old topology guard.
  - Serialization/info payloads now include dependency diagnostics.
- Extended CLI syntax for cross-tier dependency input:
  - `server/src/cli/index.ts`
  - `--depends-on` now supports entries like `id@tier#reason` (still backward-compatible with plain IDs).
- Updated HTTP task creation + diagnostics surface:
  - `server/src/routes/tasks.ts`
  - `POST /projects/:projectId/tasks` accepts `dependencyNodeRefs`.
  - Uses shared graph validator for deterministic cycle/validation behavior.
  - Added `GET /tasks/:taskId/dependency-diagnostics`.
- Updated HTTP plan approval materialization:
  - `server/src/routes/plans.ts`
  - Uses proposed-node DAG validation, persists dependency reasons into metadata for created nodes.
- Updated automation visibility diagnostics payloads:
  - `server/src/services/automationVisibility.ts`
  - Waiting diagnostics now include unresolved dependency IDs and detailed unresolved dependency entries with reasons and statuses, plus lineage context.

## Remaining risks or follow-ups
- Runtime gating still relies primarily on `task_dependencies` (task-row dependencies). Non-task tiers (`epoch`/`phase`) are represented in metadata/diagnostics but are not independently persisted as executable nodes yet.
- Cross-tier references to tiers without concrete node stores are currently validated structurally; if strict referential integrity is later required for those tiers, dedicated storage/lookup will be needed.
- Dependency diagnostics endpoint currently exists in task routes; if parity is desired, add dedicated plan diagnostics routes (or shared route-level abstraction).
- Additional unit tests focused directly on `dependencyGraph.ts` traversal edge-cases (beyond integration-level coverage) would improve long-term regression safety.
