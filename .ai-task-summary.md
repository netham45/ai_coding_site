# Task Summary

## Goal and outcome
- Goal: Add clear event records and API/CLI visibility for orchestration and automation actions (auto-extract, auto-approve, auto-start children, auto-merge plan, retries, conflicts), and show why plans/tasks are waiting with blocker context.
- Outcome: Implemented shared automation visibility payloads across CLI and HTTP, added new orchestration/queue event records, and surfaced waiting diagnostics (including dependency blocker ids/details and latest automation step) in review/info responses.

## Key code changes
- Added `server/src/services/automationVisibility.ts` (new):
  - Builds `automation` payload (`lastAction`, `recentActions`) from relevant event types.
  - Builds `waiting` diagnostics (`reasonCode`, `reason`, `dependencyBlockerTaskId`, `blockingDependencies`, `pendingChildren`, `latestTransition`, `lastAutomationAction`).
  - Adds `orchestration` snapshot from `plan_orchestration_state` for plan tasks.

- Updated `server/src/application/cliServices.ts`:
  - `getTaskInfo`, `getTaskDetails`, and `getPlan` now include `automation`, `waiting`, and `orchestration`.
  - `maybeAdvanceParentPlanAfterChildMerge(...)` now records `plan.auto_merge_on_complete.started` before auto-merge attempt.

- Updated `server/src/routes/tasks.ts`:
  - `GET /tasks/:taskId` response now includes `automation`, `waiting`, and `orchestration`.

- Updated `server/src/routes/plans.ts`:
  - `GET /plans/:planId` response now includes `automation`, `waiting`, and `orchestration`.

- Updated `server/src/services/planOrchestrator.ts`:
  - Added orchestration event records:
    - `plan.orchestration.retry.started`
    - `plan.orchestration.auto_extract.succeeded|failed`
    - `plan.orchestration.auto_approve.succeeded|failed`

- Updated `server/src/services/queue.ts`:
  - Added queue and child auto-start event records:
    - `task.queue.dispatch.succeeded|failed`
    - `plan.auto_start_child.started|failed`

- Updated `server/src/integration.test.ts`:
  - Extended review-command test assertions for waiting/blocker diagnostics and automation visibility fields.
  - Extended orchestration test assertions for new `plan.orchestration.*` events.

## Tests/validation performed
- From `/server`:
  - `npm run cli -- --help` (passed)
  - `npm run build` (passed)
  - `npm test` (passed)
- Final result: `19/19` tests passed, `0` failures.

## Remaining risks or follow-ups
- Automation visibility is derived from event naming conventions; future automation events should follow consistent prefixes to remain visible without updating filters.
- Waiting diagnostics are snapshot-based and process-local; no cross-process event coalescing was added.
- API/CLI payloads now include richer fields; if strict consumers assume fixed schemas, they should be validated against the new response shapes.
