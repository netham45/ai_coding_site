## Goal and outcome
- Goal: Implement node metadata schema and storage over existing tables without introducing new storage primitives, while preserving backward compatibility.
- Outcome: Added `tasks.metadata_json` storage and a typed orchestration metadata utility, wired metadata creation/serialization through CLI and API task/plan flows, and shipped migration coverage for schema upgrade and rollback safety.

## Key code changes
- Added node metadata types and task row metadata field:
  - `server/src/types.ts`
  - Introduced `NodeTier`, `NodeDependencyRef`, `NodeMetadata`, and optional `TaskRow.metadata_json`.
- Added orchestration metadata utility layer:
  - `server/src/services/orchestration/metadata.ts`
  - Provides normalized metadata read/write/serialize helpers, tier inference (`plan`/`task`/`exec`), idempotency fingerprint defaults, same-tier dependency normalization, and events fallback when DB metadata is missing.
- Extended database schema and migrations:
  - `server/src/db/migrations.ts`
  - Added `tasks.metadata_json TEXT NOT NULL DEFAULT '{}'` to baseline schema and `projectTaskMetadataMigration` (`ALTER TABLE ... ADD COLUMN`).
- Upgraded project DB migration/versioning behavior:
  - `server/src/db/projectDb.ts`
  - Bumped `PROJECT_DB_SCHEMA_VERSION` to `2`.
  - Added conditional migration logic to add `metadata_json` only when absent.
  - Ensured migration transaction updates `user_version` and `project_metadata.schema_version` safely.
- Extended legacy split-persistence copy/verification logic:
  - `server/src/db/projectDataMigration.ts`
  - Carries `tasks.metadata_json` when present in legacy source DB.
  - Falls back to `'{}'` when migrating from older sources without the column.
  - Included `metadata_json` in task checksum/verification paths.
- Wired metadata persistence and response serialization across runtime surfaces:
  - `server/src/application/cliServices.ts`
  - `server/src/routes/tasks.ts`
  - `server/src/routes/plans.ts`
  - Task/plan creation and plan approval child materialization now set `metadata_json` with normalized initial metadata.
  - Serialized task payloads now include `nodeMetadata`.

## Remaining risks or follow-ups
- Current API/CLI payload schema validation does not yet enforce full metadata contract semantics (e.g., strict validation for budgets/orchestration/idempotency field shapes).
- Existing historical tasks with empty/default metadata rely on normalization fallbacks; if strict metadata invariants are required later, add explicit backfill tooling.
- If richer cross-tier dependency reasoning is needed, add dedicated validation and consistency checks against DAG state rather than storing only references/reasons.
- Consider adding targeted unit tests for `services/orchestration/metadata.ts` normalization and fallback behavior to complement integration coverage.
