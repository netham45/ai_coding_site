# Task Summary

## Goal and outcome
- Goal: implement a staged split-persistence rollout with feature flags for read validation, write cutover, and cleanup, with rollback behavior that can temporarily route reads/writes back to monolith tables when migration verification fails.
- Outcome: completed. A central split-persistence policy now controls project-vs-monolith routing across routes and background services, uses migration status (`project_data_migrations`) to gate cutover, and automatically falls back to monolith storage when project DB cutover is unsafe or unavailable.

## Key code changes
- Added `server/src/db/splitPersistence.ts`:
  - Added phase model via `SPLIT_PERSISTENCE_PHASE` with supported values: `monolith`, `read_validation`, `write_cutover`, `cleanup`.
  - Added `resolveProjectDatabase(...)` to select backend (`project` or `monolith`) per project and intent.
  - Added migration-status-aware gating: project DB is only used when status is `verified`/`cleaned`; failed/in-progress/pending routes to monolith fallback.
  - Added project DB unavailable fallback behavior (when monolith tables exist) to support operational rollback.
  - Added legacy table detection so monolith fallback is only used when required monolith tables are present.
- Updated `server/src/db/index.ts`:
  - Exported split-persistence resolver, phase helpers, and related types.
- Updated `server/src/db/projectDataMigration.ts`:
  - Cleanup enablement now honors split-persistence cleanup phase (`SPLIT_PERSISTENCE_PHASE=cleanup`) in addition to `PROJECT_DATA_MIGRATION_CLEANUP_LEGACY=1`.
- Updated `server/src/routes/tasks.ts`:
  - Replaced direct project DB opens with phase-aware resolver routing.
  - Threaded read/write intent through access helpers.
  - Added `project_id` filtering to task lookup by ID so monolith fallback cannot mis-resolve tasks across member projects.
- Updated `server/src/routes/plans.ts`:
  - Replaced direct project DB opens with phase-aware resolver routing.
  - Threaded read/write intent through access helpers.
  - Added `project_id` filtering to plan lookup by ID for safe monolith fallback behavior.
- Updated `server/src/services/queue.ts`:
  - Queue scanning now uses phase-aware backend resolution per project.
- Updated `server/src/services/runtime.ts`:
  - Runtime task/project context resolution now uses phase-aware backend resolution.
  - Added backend-aware project config loading so monolith fallback can still build effective prompts from app DB config columns.
  - Added backend/context propagation for runtime follow-on calls.
- Updated `server/src/ws/terminalGateway.ts`:
  - Terminal task resolution now uses phase-aware backend routing with project-scoped lookup safety.
- Updated `server/src/index.ts`:
  - IDE heartbeat failure persistence now uses phase-aware backend resolution.

## Tests/validation performed

## Remaining risks or follow-ups
- In `read_validation` phase, traffic remains on monolith to avoid read/write split-brain; if dual-read/compare telemetry is desired, an explicit shadow-read path is still needed.
- Rollback policy currently keys off migration status + backend availability; if finer controls are needed, add explicit override flags (for example force-monolith per project).
- No dedicated automated tests were added yet for:
  - phase transitions (`monolith` -> `read_validation` -> `write_cutover` -> `cleanup`),
  - per-project rollback behavior on `failed` migration status,
  - project DB unavailable fallback paths in routes/runtime/queue/terminal,
  - mixed backends across many projects.
