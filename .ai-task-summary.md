## Goal and outcome
- Goal: Add a PATH-friendly `acs` executable so users can run CLI commands directly (instead of only `npm run cli -- ...`), while preserving backward compatibility and root-discovery behavior.
- Outcome: Implemented a dedicated executable wrapper, wired package/bin + scripts, updated usage docs/text to prefer `acs`, and validated both dev/dist invocation paths and workspace-root failure behavior.

## Key code changes
- Added executable wrapper:
  - `server/bin/acs.js`
  - Includes shebang and executable permissions.
  - Performs workspace root discovery from `process.cwd()` using the same durable markers (`package.json` workspace identity + required top-level dirs).
  - Fails clearly with exit code `1` when run outside an `ai-coding-site` workspace.
  - Bootstraps CLI entrypoint by preferring built output (`dist/cli/index.js`) and falling back to dev source via `tsx src/cli/index.ts`.

- Wired package/bin and preserved npm-script compatibility:
  - `server/package.json`
  - Added:
    - `"bin": { "acs": "./bin/acs.js" }`
  - Updated script:
    - `"cli": "node ./bin/acs.js"`
  - Result: existing `npm run cli -- ...` usage still works, now through the wrapper.

- Updated CLI usage documentation/examples to prefer `acs`:
  - `README.md`
    - Primary usage now shows `acs <command>`.
    - Explicit backward-compatible fallback retained: `npm run cli -w server -- <command>`.
    - Command examples and help reference switched to `acs`.
  - `docs/cli-command-architecture.md`
    - Updated implementation note to explicitly call for a PATH-friendly `acs` with npm fallback.

- Updated generated runtime/planner usage text to prefer `acs` while preserving fallback guidance:
  - `server/src/services/promptBuilder.ts`
  - `server/src/application/cliServices.ts`
  - `server/src/routes/plans.ts`

- Added integration tests for wrapper behavior:
  - `server/src/integration.test.ts`
  - New helper `runAcsFromCwd(...)` to execute `node server/bin/acs.js ...`.
  - Added tests:
    - `acs wrapper works from nested server directories`
    - `acs wrapper fails clearly outside the workspace`
  - Included env normalization for relative test env roots so wrapper tests run from nested cwd reliably.

## Tests/validation performed
- CLI help via backward-compatible script:
  - `npm run -s cli -- --help` (from `server/`)
  - Result: success; full command list printed.

- Direct wrapper help:
  - `node ./bin/acs.js --help` (from `server/`)
  - Result: success; same command list printed.

- Integration tests (CLI suite):
  - `npm run -s test -- --test-name-pattern "CLI subcommands"`
  - Result: pass, including new `acs` wrapper tests.

- TypeScript build:
  - `npm run build` (in `server/`)
  - Result: pass.

- File/executable check:
  - Verified `server/bin/acs.js` exists with executable bit in this environment.

## Remaining risks or follow-ups
- The wrapper currently duplicates workspace-root detection logic rather than importing shared `workspaceRoot.ts`; this avoids TypeScript runtime coupling in the bin script, but means marker updates must be kept in sync in two places.
- Dist-vs-src resolution is presence-based (`dist/cli/index.js` first). If build output layout changes, update wrapper paths.
- If desired, add an explicit installation note for global/local PATH usage (`npm link`, `npx acs`, or workspace bin path) to complement current command examples.
