# Task Summary

## Goal and outcome
- Goal: Refactor plan approval in both route and CLI service paths so approved revision items are created correctly as execution tasks or plan tasks, with dependency wiring preserved for mixed graphs, correct nested-plan git/workspace topology, and sane auto-merge defaults when parent plan auto-start is enabled.
- Outcome: Updated both approval implementations to apply parent-plan auto-start as a default auto-merge hint for child execution tasks while preserving parsed-item overrides and manual key overrides, and ensured plan workspaces are initialized with `.ai-plan` even when creation is deferred by dependencies.

## Key code changes
- `server/src/routes/plans.ts`
  - In `/plans/:planId/approve`, added `defaultExecutionAutoMerge = Boolean(plan.auto_start)`.
  - Updated child execution-task auto-merge resolution to include three sources:
    - explicit approve payload `autoMergeItemKeys`,
    - parsed revision item `autoMerge`,
    - new fallback `defaultExecutionAutoMerge` when parent plan has `auto_start` enabled.
  - Kept mixed item-type creation (`mode = 'execution' | 'plan'`), dependency mapping via `task_dependencies`, and nested topology selection logic intact.

- `server/src/application/cliServices.ts`
  - In `approvePlan`, mirrored the same `defaultExecutionAutoMerge = Boolean(plan.auto_start)` behavior.
  - Updated child execution-task auto-merge resolution to match route behavior exactly (payload overrides, parsed defaults, then parent auto-start fallback).
  - Preserved existing mixed item creation flow and dependency wiring.

- `server/src/services/runtime.ts`
  - In `startTaskRuntime`, when lazily creating a missing workspace git clone, now creates `.ai-plan` for `mode === 'plan'`.
  - This covers blocked plan children (not cloned at approval time) so they still get proper plan workspace layout when they later become runnable.

## Remaining risks or follow-ups
- No dedicated integration test yet verifies this new fallback rule end-to-end: parent plan `auto_start=true` causing child execution tasks to default `auto_merge=true` on approve in both route and CLI paths.
- Existing auto-merge precedence now effectively favors enabling auto-merge when any source indicates true; if future requirements need stricter override semantics (for example, explicit false in one source), this merge policy should be formalized.
- Mixed dependency wiring remains task-based and assumes all approved items materialize in `tasks`; if future architecture introduces separate storage for plan children, dependency persistence and queue behavior will need revisiting.
