## Goal and outcome
- Goal: Implement deterministic checks that can block stage progression until another stage is complete or a node is merged, and ensure checks are re-evaluated on relevant events instead of relying on polling-only delays.
- Outcome: `stage_complete` and `node_merged` checks are now enforced as deterministic stage gates in the workflow engine. Re-evaluation occurs on `handleEvent(...)` calls (including a new run-level `workflow.node.merged` event), allowing blocked stages to unblock immediately when conditions become true.

## Key code changes
- Updated workflow engine stage-definition model and parsing:
  - `server/src/services/workflowEngine.ts`
  - Added `deterministicChecks` to `WorkflowEngineStageDefinition`.
  - Added parsing/normalization of deterministic checks from JSON stage definitions via `deterministic_checks`, `deterministicChecks`, or `checks`.
- Added deterministic check gating in stage scheduling:
  - `server/src/services/workflowEngine.ts`
  - Added `deterministicCheckGate(...)` that runs `runDeterministicChecksForStageRun(...)` and inspects pass/fail outcomes.
  - `tickWorkflowRun(...)` now blocks pending stages when deterministic checks fail, emits blocked lifecycle reason `deterministic_checks_pending`, and includes failed check names in lifecycle payload.
  - Stage start now requires both dependency resolution and deterministic check pass.
- Added event-driven recheck pathway and idempotency for run-level events:
  - `server/src/services/workflowEngine.ts`
  - Extended event union with `workflow.node.merged`.
  - `handleEvent(...)` now supports events without `stageRunId` for `workflow.node.merged`.
  - Added run-level idempotency dedupe helper `hasDuplicateRunEventByIdempotency(...)`.
  - Event handling continues into `tickWorkflowRun(...)`, causing immediate re-evaluation after relevant events.
- Added/extended tests:
  - `server/src/services/workflowEngine.test.ts`
  - New test: `stage_complete and node_merged checks unblock via event-driven rechecks`.
  - Verifies:
    - Initially blocked gate stage with failing `stage_complete` and `node_merged` checks.
    - Re-evaluation after `workflow.stage.verify_succeeded` flips `stage_complete` to pass while `node_merged` remains fail.
    - Re-evaluation after `workflow.node.merged` flips `node_merged` to pass and unblocks/runs stage.

## Research performed for this task and the key findings
- Reviewed deterministic check runner implementation:
  - `server/src/services/workflowChecks.ts`
  - Finding: all required deterministic checks already existed and persisted results, but engine integration for gating/rechecks was not wired.
- Reviewed workflow engine orchestration behavior:
  - `server/src/services/workflowEngine.ts`
  - Finding: engine handled dependencies/lifecycle/attempts/idempotency, but did not evaluate deterministic checks for stage admission.
- Reviewed tests and repository APIs:
  - `server/src/services/workflowEngine.test.ts`
  - `server/src/services/workflowChecks.test.ts`
  - `server/src/services/workflowRepository.ts`
  - Finding: adequate primitives existed to persist and query check outcomes; missing piece was event-driven orchestration wiring.
- Verified schema constraints for events/check results:
  - `server/src/db/migrations.ts`
  - Finding: `workflow_check_results` and `workflow_events` tables already support this behavior without schema migration.

## Questions answered during this task, including each answer
- Q: Were `stage_complete` and `node_merged` checks already implemented?
  - A: Yes, in `workflowChecks.ts`; they were not yet used by the engine as stage gates.
- Q: Was re-evaluation already triggered by events?
  - A: Partially for stage transitions via `tickWorkflowRun(...)`, but not with deterministic check gating integrated; therefore unblocking based on those checks was not event-driven.
- Q: How should node-merge-triggered unblocking be modeled?
  - A: Added explicit run-level event support (`workflow.node.merged`) in `handleEvent(...)`, then rely on immediate `tickWorkflowRun(...)` to re-evaluate deterministic checks and unblock stages.
- Q: Were DB schema changes needed?
  - A: No schema changes were required.

## Remaining risks or follow-ups
- YAML stage-definition parsing remains lightweight and currently does not parse nested YAML check blocks; deterministic-check parsing is fully supported in JSON-form definitions (stringified JSON currently used by tests).
- `workflow.node.merged` is modeled as a generic run-level trigger; if future requirements need selective recheck targeting, payload-based filtering/routing could be added.
- Current implementation re-evaluates pending stages during each tick; for very large workflows, future optimization may be needed to narrow recheck scope to impacted stages.
