## Goal and outcome
- Goal: Add APIs to manage workflow definitions and workflow runs (definitions CRUD, run start/tick/cancel, node workflow status), and ensure responses include full run/stage state with stage-by-stage diagnostics and typed/validated contracts.
- Outcome: Implemented new workflow HTTP endpoints under existing task routes, added zod contracts for typed request/response validation, added run/stage serializers that include diagnostics payloads, and added focused route tests to verify the new API behavior.

## Key code changes
- Added workflow API contracts:
  - `server/src/api/contracts/workflows.ts`
  - Introduced zod schemas for:
    - Workflow definition create/patch payloads
    - Workflow run start/cancel payloads
    - Workflow run/stage/check/event/diagnostics response shapes
- Extended task routes with workflow APIs:
  - `server/src/routes/tasks.ts`
  - Added:
    - Definitions endpoints:
      - `GET /api/projects/:projectId/workflow-definitions`
      - `POST /api/projects/:projectId/workflow-definitions`
      - `GET /api/projects/:projectId/workflow-definitions/:definitionId`
      - `PATCH /api/projects/:projectId/workflow-definitions/:definitionId`
      - `DELETE /api/projects/:projectId/workflow-definitions/:definitionId`
    - Run endpoints:
      - `GET /api/projects/:projectId/workflow-runs`
      - `POST /api/projects/:projectId/workflow-runs/start`
      - `GET /api/projects/:projectId/workflow-runs/:runId`
      - `POST /api/projects/:projectId/workflow-runs/:runId/tick`
      - `POST /api/projects/:projectId/workflow-runs/:runId/cancel`
    - Node status endpoint:
      - `GET /api/nodes/:nodeId/workflow-status`
  - Added serialization helpers that return full run + definition + stages + events, including stage diagnostics:
    - lifecycle state
    - attempts started
    - blocked dependencies
    - check results
    - recent stage events
  - Wired route logic to existing repository and engine services:
    - `workflowRepository` CRUD/transition functions
    - `workflowEngine.startWorkflowRun` and `workflowEngine.tickWorkflowRun`
- Added focused route tests:
  - `server/src/routes/workflowApis.test.ts`
  - Covers definition CRUD, run start/tick/cancel, and node workflow status diagnostics behavior.

## Questions answered during this task, including each answer
- Q: Are workflow CRUD/run/status endpoints already implemented?
  - A: No. They were not present in route handlers and had to be added.
- Q: Where should typed validation contracts live?
  - A: In a dedicated contracts module under `server/src/api/contracts/`, consistent with existing orchestration contract organization.
- Q: How should “stage-by-stage diagnostics payloads” be represented?
  - A: As derived per-stage diagnostics including lifecycle state, attempts count, blocked-by dependencies, check results, and recent stage events.
- Q: Should run start invoke the engine immediately?
  - A: Yes. `POST .../workflow-runs/start` creates the run and then calls `startWorkflowRun(...)` to initialize and tick progression.

## Remaining risks or follow-ups
- Workflow endpoints are currently located in `tasks` routes for integration simplicity; could be moved to a dedicated `workflows` router for clearer separation.
- Stage diagnostics are derived from persisted events/checks and currently expose recent slices (`recentEvents`, run `events`), not full history; pagination/filtering endpoints may be needed for large runs.
- Cancel behavior marks pending/running stages as cancelled and transitions run to cancelled; if future policy requires richer cancellation semantics (e.g., async worker interrupts), additional orchestration hooks may be required.
- No OpenAPI/SDK generation is wired from the new zod schemas yet; if external clients rely on generated contracts, add schema export integration.
