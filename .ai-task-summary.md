## Goal and outcome
- Goal: Execute the prompt to refactor start behavior so planning tiers (`epoch`/`phase`/`plan`) start via workflow runs instead of legacy direct runtime-session starts, while keeping `task`/`exec` compatible with runtime-backed stage behavior.
- Outcome: The runtime code paths were already aligned for planning tiers (workflow-first in API/CLI/queue). The remaining mismatch was in integration tests that still expected direct runtime sessions for planning nodes. Those tests were updated to assert workflow-run startup and use file-based plan YAML inputs. Targeted validations passed.

## Key code changes
- Updated integration tests in `server/src/integration.test.ts`:
  - Renamed and revised test:
    - From: `start triggers runtime session for non-exec and extract surfaces YAML proposed children`
    - To: `start routes planning tiers through workflow runs and extract surfaces YAML proposed children`
  - Replaced planning-tier runtime-session assertions with workflow assertions:
    - Asserted a `workflow_runs` row exists and is `running` for the started planning node.
    - Asserted `orchestration.manual_start` event payload uses `strategy: "workflow_engine"`.
  - Changed plan extraction setup in two tests to seed `.ai-plan/latest-plan.yaml` directly in workspace and assert extraction source is `file`.
  - Removed reliance on `task_sessions.last_output` for planning-tier start tests.

- Legacy direct runtime start behavior for planning tiers was effectively disabled in the core start code.
- Failing behavior was test expectations still waiting for direct runtime sessions on planning nodes.
- `extractPlan` supports file-first resolution (`.ai-plan/latest-plan.yaml`) before session output, so tests can be made workflow-consistent without direct runtime-session dependence.

## Questions answered during this task, including each answer
- Q: Is runtime-start routing for planning tiers still present in the start endpoint/service paths?
  - A: No. Planning tiers route to workflow start; runtime start is used for non-planning tiers.
- Q: Do we need to patch runtime start logic for this prompt?
  - A: Not in core start code. The required change was primarily aligning integration tests with existing workflow-first behavior.
- Q: Should planning-tier extract tests depend on runtime session output?
  - A: Not required. File-based plan YAML (`.ai-plan/latest-plan.yaml`) is supported and better reflects workflow-driven planning.
- Q: Does API start coverage still validate manual-start auditing?
  - A: Yes. Existing manual override/start test still passes and includes `orchestration.manual_start` assertions.
