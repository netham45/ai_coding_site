## Goal and outcome
- Goal: Introduce a cutover flag so legacy `plan_orchestration_pass` ownership can be disabled, with workflow engine ownership as the primary path and a safe rollback switch.
- Outcome: Implemented `ORCHESTRATION_LEGACY_PLAN_ORCHESTRATION_PASS_ENABLED` (default off) to disable legacy plan-orchestration scheduling/worker startup by default. Rollback is supported by enabling the flag, which reactivates legacy `plan_orchestration_pass` routing safely.

## Key code changes
- Added feature flag API:
  - `server/src/config/featureFlags.ts`
  - New function: `legacyPlanOrchestrationPassOwnershipEnabled()`
  - Behavior: returns `false` by default; also forced `false` when `ORCHESTRATION_COMPATIBILITY_MODE` is enabled.
- Updated feature flag tests:
  - `server/src/config/featureFlags.test.ts`
  - Added assertions for default false, truthy env enablement, and compatibility-mode override.
- Gated legacy plan-orchestration job derivation in orchestration hooks:
  - `server/src/services/orchestration/hooks.ts`
  - `plan_orchestration_pass` job emission is now conditional on the new flag across timer tick, output updates, and general hooks.
- Updated orchestration hook tests:
  - `server/src/services/orchestration/hooks.test.ts`
  - New assertions for default cutover behavior and rollback re-enable behavior.
- Gated timer-based legacy enqueue path:
  - `server/src/services/orchestration/jobQueue.ts`
  - `startOrchestrationJobQueueWorker()` now conditionally enqueues timer-driven `plan_orchestration_pass` jobs only when rollback flag is enabled.
- Gated legacy plan orchestrator worker lifecycle:
  - `server/src/services/planOrchestrator.ts`
  - `kickPlanOrchestrationProcessing()` and `startPlanOrchestrationWorker()` return early when legacy ownership is disabled.
- Integration test coverage updates:
  - `server/src/integration.test.ts`
  - Added test: `workflow engine ownership disables legacy plan_orchestration_pass by default`.
  - Updated existing output-monitor test to explicitly set rollback flag on, validating legacy behavior remains available and stable when enabled.

Key findings:
- Legacy ownership was represented by unconditional scheduling of `plan_orchestration_pass` from hooks and timer ticks, plus unconditional startup of the legacy plan orchestration worker.
- Workflow-driven start behavior for planning tiers was already in place elsewhere (workflow-first routing), so this change needed to isolate and gate only the legacy pass ownership path.
- Existing tests assumed legacy pass availability; specific tests required explicit rollback-flag enablement after default ownership cutover.

## Questions answered during this task, including each answer
- Q: Where is legacy `plan_orchestration_pass` ownership actually exercised?
  - A: In hook-derived job scheduling, timer tick enqueue in job queue, and plan orchestrator worker startup/kick paths.
- Q: Should cutover disable workflow engine behavior too?
  - A: No. The cutover only gates legacy `plan_orchestration_pass` ownership; workflow engine ownership remains active.
- Q: How should rollback be implemented safely?
  - A: Via a dedicated env flag (`ORCHESTRATION_LEGACY_PLAN_ORCHESTRATION_PASS_ENABLED`) that conditionally re-enables all legacy scheduling and worker startup points.
- Q: What should the default be to satisfy “workflow engine sole owner”?
  - A: Flag default is `false`, which suppresses legacy pass ownership by default.
