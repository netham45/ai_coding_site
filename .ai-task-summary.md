## Goal and outcome
- Goal: Define and enforce a deterministic lifecycle state machine (`draft|ready|blocked|running|complete|failed|canceled`) while preserving compatibility with existing task statuses, and ensure parent plan completion is gated by synthesize+verify rather than child completion alone.
- Outcome: Added a dedicated orchestration state machine with explicit transition guards, integrated it into CLI status transition paths, added lifecycle traceability signals, and enforced parent completion guards. Existing API/CLI compatibility was preserved via legacy-to-lifecycle mapping.

## Key code changes
- Added deterministic state machine and guard utilities:
  - `server/src/services/orchestration/stateMachine.ts`
  - Includes:
    - legacy task status -> lifecycle mapping
    - lifecycle transition table enforcement
    - explicit illegal transition errors
    - dependency/children blocking guards
    - parent synthesis+verification completion guards
- Extended metadata typing for lifecycle traceability:
  - `server/src/types.ts`
  - Added optional `NodeMetadata.lifecycle` fields:
    - `synthesis_passed`
    - `verification_passed`
    - `last_transition_reason_code`
- Integrated guarded transitions across CLI orchestration flows:
  - `server/src/application/cliServices.ts`

    - validate transitions through state machine before write

  - Replaced direct merge status writes with guarded transition helper for conflict/success paths.
  - Parent auto-advance now catches/records completion-guard blocks (`plan.parent_completion.blocked`).
  - Added lifecycle metadata updates after plan synthesis/verification milestones:
    - `extractPlan` marks synthesis pass
    - `approvePlan` marks synthesis+verification pass
- Extended automation diagnostics visibility:

## Remaining risks or follow-ups
- Runtime and route layers still contain independent status mutation logic outside this CLI-focused integration; full system-wide determinism would benefit from routing all status transitions through a shared state-machine gateway.
- Legacy status vocabulary remains in storage/API for compatibility; if a future migration adopts lifecycle states as first-class persisted fields, additional migration/backfill and compatibility shims will be needed.
- Parent synth/verify guard currently infers success from metadata and revision states; if stricter provenance is needed, consider dedicated signed transition artifacts or stronger verification event contracts.
- Transition reason codes are now standardized in CLI transition recording; parity across all non-CLI paths should be audited to ensure consistent observability.
