## Goal and outcome
- Goal: Add persistence for `workflow_definitions`, `workflow_runs`, `workflow_stage_runs`, `workflow_check_results`, and `workflow_events`, including repository CRUD and run/stage state transition handling.
- Outcome: Implemented schema support (baseline + upgrade path), a typed workflow repository layer with transition guards, and tests covering round-trip persistence and status transition integrity.

    - `workflow_definitions`
    - `workflow_runs`

## Research performed for this task and the key findings
- Inspected current DB/migration architecture and upgrade strategy:
  - `server/src/db/migrations.ts`, `server/src/db/projectDb.ts`, `server/src/db/appDb.ts`
- Inspected existing orchestration persistence/event patterns to align style:
  - `server/src/services/events.ts`, `server/src/services/orchestration/*`
- Reviewed split-persistence and migration-backfill assumptions:
  - `server/src/db/splitPersistence.ts`, `server/src/db/projectDataMigration.ts`
- Key findings:
  - No existing workflow persistence tables/repository were present.
  - Project DB uses versioned `user_version` upgrades; additive schema should be introduced via a new upgrade step.
  - App DB has legacy migration compatibility hooks that need matching table creation to avoid drift.
  - Existing codebase pattern favors direct SQL repositories with typed rows and explicit transition guards.

## Questions answered during this task, including each answer
- Q: Where should workflow persistence schema be added?
  - A: Add to `projectBaselineMigration` and mirror in legacy app migration helpers for compatibility.
- Q: How should existing project DBs receive workflow tables?
  - A: Add `upgradeProjectDbToV3()` and bump `PROJECT_DB_SCHEMA_VERSION` to `3`.
- Q: What transition semantics should run/stage status updates use?
  - A: Enforce explicit allow-lists:
    - Runs: `queued -> running/cancelled`, `running -> succeeded/failed/cancelled`, terminal states self-only.
    - Stage runs: `pending -> running/skipped/cancelled`, `running -> succeeded/failed/cancelled`, terminal states self-only.
- Q: How should transition changes be audited?
  - A: Write transition events to `workflow_events` with from/to status and reason payload.
- Q: Did the task require wiring the new repository into routes/CLI flows?
  - A: No explicit requirement in prompt; task focused on persistence/repository layer and status integrity tests.
