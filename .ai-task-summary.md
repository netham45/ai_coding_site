## Goal and outcome
- Goal: Implement a `WorkflowEngine` with `startWorkflowRun`, `tickWorkflowRun`, and `handleEvent` that enforces workflow/stage transitions, dependency gates, attempt limits, retry behavior, and idempotency under repeated ticks/events.
- Outcome: Added a new workflow engine service and test suite. Stage progression now works end-to-end across dependent stages, blocked/waiting_input/verifying lifecycle states are tracked via workflow events, retry handling honors per-stage max attempts, and duplicate ticks/events are handled idempotently.

## Key code changes
- Added new engine service:
  - `server/src/services/workflowEngine.ts`
  - Exports:
    - `startWorkflowRun(...)`
    - `tickWorkflowRun(...)`
    - `handleEvent(...)`
- Implemented workflow definition parsing for stage metadata from `definition_yaml`:
  - Supports stage key/id extraction.
  - Supports dependency extraction (`depends_on` / `dependsOn`).
  - Supports attempt-limit extraction (`max_attempts` / `maxAttempts`).
- Implemented start behavior:
  - Creates missing `workflow_stage_runs` from definition.
  - Transitions run `queued -> running`.
  - Performs initial tick.
- Implemented tick behavior:
  - Enforces dependency gating for pending stages.
  - Emits stage lifecycle events (`workflow.stage.lifecycle`) with states:
    - `blocked`
    - `ready`
    - `running`
  - Starts one runnable stage at a time.
  - Records attempt starts with `workflow.stage.attempt.started`.
  - Transitions workflow run to:
    - `failed` if any stage fails
    - `succeeded` when all stages are no longer pending and none failed
- Implemented event handling behavior:
  - Supports events:
    - `workflow.stage.waiting_input`
    - `workflow.stage.input_received`
    - `workflow.stage.verifying`
    - `workflow.stage.verify_succeeded`
    - `workflow.stage.verify_failed`
  - Tracks waiting/verifying/running lifecycle changes through `workflow.stage.lifecycle` events.
  - On verify success: transitions stage to `succeeded`.
  - On verify failure:
    - If retryable and attempts remain: schedules retry, records next attempt, keeps stage running.
    - Otherwise: transitions stage to `failed`.
  - Calls `tickWorkflowRun(...)` after event handling to continue progression.
- Implemented idempotency protections:
  - Event-level dedupe by `eventId` (no-op if already persisted).
  - Stage-event dedupe by `idempotencyKey` + `eventType` on a stage.
  - Repeated ticks while a stage is already running do not create extra attempts.
- Added test coverage:
  - `server/src/services/workflowEngine.test.ts`
  - Covers:
    - end-to-end dependency-gated stage progression
    - blocked/waiting_input/verifying lifecycle transitions
    - retry and max-attempt exhaustion behavior
    - idempotency under repeated ticks and duplicate events

## Questions answered during this task, including each answer
- Q: Does a `WorkflowEngine` already exist and need extension?
  - A: No. There was no existing `WorkflowEngine` with the required entry points.
- Q: Where should run/stage transition enforcement live?
  - A: In the new engine service, while using existing repository transition APIs to preserve integrity checks.
- Q: How should blocked/waiting_input/verifying be represented when stage status values are coarse (`pending/running/succeeded/...`)?
  - A: As explicit lifecycle workflow events (`workflow.stage.lifecycle`) associated with stage runs.
- Q: How should retry and attempt caps be enforced?
  - A: Track attempts via `workflow.stage.attempt.started` event count and compare against per-stage `max_attempts`.
- Q: How should idempotency be enforced for repeated inputs?
  - A: Use `eventId` dedupe and `idempotencyKey`+`eventType` dedupe on stage events; repeated ticks avoid duplicating attempts while stage is already running.

## Remaining risks or follow-ups
- Engine currently infers stage definitions from `definition_yaml` with lightweight parsing; a stricter schema/parser may be needed if workflow definition complexity increases.
- Lifecycle states (`blocked`, `waiting_input`, `verifying`) are represented as events, not additional DB status enums; consumers must read event history (or derived state) to observe them.
- The engine is implemented and tested at service level; integration into higher-level runtime/worker/API invocation paths is a follow-up if not already wired externally.
- Retry policy currently hinges on incoming event payload (`retryable`) and per-stage attempt limits; richer policy inputs (error-class mapping/backoff scheduling) may be needed later.
