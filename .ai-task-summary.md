# Task Summary

## Goal and outcome
- Goal: Implement an idempotent plan orchestration service that automatically advances eligible plan tasks from `waiting_input` (when `.ai-plan/latest-plan.yaml` exists) through revision extraction and approval, then relies on the existing queue/runtime pipeline to start child items safely.
- Outcome: Added a new orchestration worker with persistent DB lock/state and output-hash dedupe, wired it into startup, and validated duplicate-safe behavior with integration tests.

## Key code changes
- `server/src/services/planOrchestrator.ts` (new)
  - Added periodic orchestration pass for `mode='plan'`, `auto_start=1`, `status='waiting_input'` plans.
  - Reads `.ai-plan/latest-plan.yaml`, computes normalized SHA-256, and avoids re-processing unchanged approved output.
  - Uses per-plan DB lock claim/release with expiry for retry-safe concurrent passes.
  - Calls existing `extractPlan` and `approvePlan` flows to preserve mixed-item creation and dependency wiring.
  - Persists orchestration progress/failure state (`last_extracted_revision_id`, `last_approved_revision_id`, `last_approved_output_sha256`, `last_failed_output_sha256`, `last_error`).

- `server/src/db/migrations.ts`
  - Added `plan_orchestration_state` table and lock-expiry index.

- `server/src/types.ts`
  - Added `PlanOrchestrationStateRow` type.

- `server/src/index.ts`
  - Started orchestrator worker (`startPlanOrchestrationWorker`) with existing background workers.

- `server/src/integration.test.ts`
  - Added orchestration integration test verifying two passes do not duplicate extraction/approval or child task creation for identical plan output.

- `server/src/application/cliServices.ts`
- `server/src/routes/plans.ts`
  - Fixed plan-approval `INSERT INTO tasks` placeholder mismatch so child task creation does not fail (`23 values for 24 columns`).

## Remaining risks or follow-ups
- Orchestrator intentionally requires `.ai-plan/latest-plan.yaml`; it does not auto-approve from raw session output fallback.
- Failed outputs are deduped by hash (`last_failed_output_sha256`) and will not be retried until plan output changes.
- Locking is TTL-based; very long operations may rely on subsequent safe retries.
- Additional telemetry/metrics around orchestration throughput/failure rates could improve operability.
