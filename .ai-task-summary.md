## Goal and outcome
- Goal: On stage idle/waiting_input, run `expected_results` evaluation automatically; feed failed-check reasons back as runtime input; auto-advance when checks pass.
- Outcome: Implemented auto-verification on waiting_input cadence in the workflow engine. Failed expected-results checks now emit actionable runtime feedback events, and passing checks automatically complete the stage and advance workflow progression.

## Key code changes
- Updated `server/src/services/workflowEngine.ts`:
  - Added `expectedResults` to `WorkflowEngineStageDefinition`.
  - Added `expected_results`/`expectedResults` parsing support in stage definition parsing.
  - Added `normalizeExpectedResults(...)` to map stage config into `DeterministicWorkflowCheck[]`.
  - Added `evaluateExpectedResultsOnTick(...)` to run deterministic checks when lifecycle is `waiting_input`.
  - Added `maybeEmitRuntimeInputFeedback(...)` to publish `workflow.stage.runtime_input.required` with per-check feedback and idempotency dedupe.
  - On check pass: emit `workflow.stage.verify_succeeded`, mark stage `succeeded`, and continue ticking to advance downstream stages.
  - On check fail: emit actionable feedback and keep stage in `waiting_input` lifecycle (stage status remains `running`).
  - Added workspace resolution for check execution via run task workspace path fallback to `process.cwd()`.
- Updated `server/src/services/workflowEngine.test.ts`:
  - Added test: waiting_input stage auto-verifies and auto-advances dependent stage.
  - Added test: failed expected_results checks emit runtime input feedback with actionable reason payload.

## Questions answered during this task, including each answer
- Q: Is `expected_results` already evaluated anywhere in workflow execution?
  - A: No. There was no existing expected-results evaluation in workflow engine ticks/events.
- Q: Where should auto-verification on idle/waiting_input be triggered?
  - A: In `tickWorkflowRun(...)`, gated by latest stage lifecycle state `waiting_input`.
- Q: How should failed checks be returned to runtime as input?
  - A: Emit `workflow.stage.runtime_input.required` with structured per-check feedback (`check`, `reason`, `details`) and idempotency key.
- Q: How should successful checks advance stages?
  - A: Mark current stage `succeeded` and immediately recurse tick progression so next unblocked stage can start.
- Q: How to avoid duplicate feedback emissions on repeated ticks?
  - A: Deduplicate feedback event creation with hash-based idempotency key over failed-check payload.

## Remaining risks or follow-ups
- `expected_results` YAML parsing currently supports JSON-style structures reliably; complex multi-line native YAML list/object forms are only lightly supported by current parser strategy.
- Feedback is emitted as workflow events (`workflow.stage.runtime_input.required`); downstream runtime consumer wiring/UX rendering must read these events to surface prompts to agents/users.
- Auto-evaluation currently triggers when lifecycle is `waiting_input`; if “idle” should include additional states/signals, expand trigger conditions in engine.
- Actionability text currently follows a generic reason pattern; richer domain-specific remediation hints may improve operator experience.
- Current built-in stage actions for `review` and `return_result` are `no_op`; if stricter semantic behavior is required, these should be replaced with concrete handlers/events.
- `run_command` currently uses `command: "true"` for deterministic success; real command execution policy may need task-specific command resolution.
- Auto-progression uses a bounded pass loop (`MAX_AUTORUN_PASSES`); very complex future workflows may need a scheduler-driven continuation model.
- Existing non-plan-created plain `task` nodes are intentionally unchanged by this work; only exec-node creation paths were wired.
