## Research Performed and Key Findings
- CLI validation:
  - Ran `npm run cli -- --help` from `/server` and confirmed command surface exactly matched prompt expectations.
- Core orchestration ownership and overlap review:
  - `server/src/services/events.ts`: every recorded event fans into orchestration jobs via `deriveOrchestrationJobsFromEvent`, which means event-triggered fanout is central and can duplicate work if ownership isn’t explicit.
  - `server/src/services/orchestration/hooks.ts`: most relevant events enqueue both `task_queue_dispatch` and `plan_orchestration_pass`; timer ticks also enqueue both. This is a major overlap point.
  - `server/src/services/orchestration/jobQueue.ts`: queue supports all legacy + hierarchical job types and timer-based enqueue for both legacy jobs; idempotency exists per event key/window but ownership semantics are not separated.
  - `server/src/services/planOrchestrator.ts`: legacy orchestrator still mutates plan behavior for `mode='plan'` tasks (auto extract/approve path), including lock/state management in `plan_orchestration_state`.
  - `server/src/services/queue.ts`: legacy dispatch for queued tasks is still active via orchestration job queue.
- Hierarchical path completeness:
  - `server/src/services/orchestration/jobs/decompose.ts`: currently a stub (emits completion with `children: []`, then re-runs readiness); does not perform real tier decomposition.
  - `evaluateReadiness.ts`: computes deterministic decisions and emits `follow_up_jobs` hints (`decompose` vs readiness retry) but does not enqueue follow-up jobs directly.
  - `reReview.ts`, `deltaPlan.ts`, `synthesize.ts`, `verify.ts`: implemented and functional, but orchestration chain has gaps due to decompose/readiness handoff incompleteness.
- Tier vs mode ambiguity:
  - `createProjectNode` in `server/src/routes/tasks.ts` maps non-`task` tiers to `mode='plan'`, so epoch/phase/plan all live in plan mode and rely on metadata tier for meaning. This is a central cutover risk.
- API/UI/compatibility posture:
  - Hierarchy/actions endpoints are feature-flag gated (`orchestrationHierarchyApiEnabled`, `orchestrationActionsApiEnabled`), with compatibility mode disabling orchestration endpoints.
  - UI components (`TaskDetailPage`, `NodeActionsPanel`, `OrchestrationTree`, `TaskSidebar`) consume orchestration/hierarchy contracts and already handle unavailable orchestration data paths.
- Parser/schema compatibility:
  - `planParser.ts` enforces top-level `tasks:` and legacy-compatible fields (`id`, `title`, `prompt`, `depends_on`) and validates cycles/missing deps. Existing extraction/approval flow depends on this contract.
- Tests reviewed:
  - `integration.test.ts` already covers legacy plan orchestration, orchestration queue idempotency/debounce, hierarchical endpoints/actions, completion artifacts, and compatibility mode gating.
