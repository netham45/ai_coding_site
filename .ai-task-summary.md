## Research performed for this task and the key findings
- Reviewed `server/src/integration.test.ts` decomposition section.
  - Finding: Existing coverage only asserted deterministic decompose paths did not synthesize children.
- Reviewed `server/src/application/cliServices.ts` (`startNode`, `extractPlan`, `reviewPlan`, `approvePlan`, `readPlanOutputSource`).
  - Findings:
    - `startNode` starts runtime and emits `orchestration.manual_start` for non-exec tiers.
    - `extractPlan` can extract from session output when plan file is absent and writes normalized `.ai-plan/latest-plan.yaml`.
    - `reviewPlan` returns proposed revision items suitable for assertions.
    - `approvePlan` materializes children from proposed revision items.
- Reviewed runtime startup behavior in `server/src/services/runtime.ts` / `runtimeWorker.ts`.
  - Findings:
    - Runtime startup is asynchronous.
    - Workspace must satisfy git preconditions for stable session creation.
    - Polling for `task_sessions` is needed for reliable assertions.

## Questions answered during this task, including each answer
- Question: Do existing tests already cover runtime start/extract/review/approve parity?
  - Answer: No; they covered only deterministic decompose non-synthesis behavior.
- Question: Which API/CLI service paths should parity coverage use?
  - Answer: `startNode`, `extractPlan`, `reviewPlan`, and `approvePlan`.
- Question: How should “inspectable decomposition output” be asserted deterministically?
  - Answer: Seed `task_sessions.last_output` with YAML, run `extractPlan`, and assert `.ai-plan/latest-plan.yaml` plus `reviewPlan` proposed items.
- Question: How to prevent race conditions around runtime session creation?
  - Answer: Add a polling helper (`waitForLatestSessionId`) and use git-initialized workspaces.
- Question: How to verify no mirrored deterministic placeholders remain?
  - Answer: Assert approved children have non-null `source_plan_item_key` and count of child rows with null `source_plan_item_key` is zero.
