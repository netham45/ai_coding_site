## Remaining risks or follow-ups
- Workflow endpoints are currently located in `tasks` routes for integration simplicity; could be moved to a dedicated `workflows` router for clearer separation.
- Stage diagnostics are derived from persisted events/checks and currently expose recent slices (`recentEvents`, run `events`), not full history; pagination/filtering endpoints may be needed for large runs.

- No OpenAPI/SDK generation is wired from the new zod schemas yet; if external clients rely on generated contracts, add schema export integration.
- Workflow stage actions are implemented at service level; higher-level automation loops that should invoke `executeWorkflowStageAction(...)` on running stage runs still need explicit orchestration wiring if not already handled elsewhere.
- `generate_plan_yaml` stage is represented as a built-in stage in definitions, but a concrete default action runner for generating YAML from runtime output is not yet wired in this task.
- Child task creation path in workflow stage action currently persists DB rows/dependencies and metadata but does not perform full git workspace initialization/branch setup used by `approvePlan(...)`; if required for immediate execution, that should be aligned.

- YAML stage-definition parsing remains lightweight and currently does not parse nested YAML check blocks; deterministic-check parsing is fully supported in JSON-form definitions (stringified JSON currently used by tests).
- `workflow.node.merged` is modeled as a generic run-level trigger; if future requirements need selective recheck targeting, payload-based filtering/routing could be added.
- Current implementation re-evaluates pending stages during each tick; for very large workflows, future optimization may be needed to narrow recheck scope to impacted stages.

## Questions answered during this task, including each answer
- Q: Do we already have API support for workflow stage diagnostics?
  - A: Yes. Existing workflow endpoints return full run/stage/check/event state, including per-stage diagnostics.

- Q: Is there existing support for selecting built-in vs custom workflow per node?
  - A: No. This had to be added via a new node workflow assignment endpoint and start-path logic updates.

- Q: Where should node workflow assignment be stored?
  - A: In node metadata (`metadata.custom.workflow_assignment`) to avoid schema migrations and align with existing orchestration metadata patterns.

- Q: How should manual continue/retry/cancel controls work?
  - A: Continue triggers run tick, retry starts a new run for the same node/definition, and cancel transitions current run to cancelled with optional reason.

- Q: Which nodes should expose workflow assignment controls?
  - A: `epoch`, `phase`, and `plan` tiers, since these are workflow-engine-capable in current orchestration behavior.
- Q: Can stage unblocking be driven immediately by a node merge event?
  - A: After implementation, yes. `handleEvent(...)` now accepts run-level `workflow.node.merged` and immediately triggers `tickWorkflowRun(...)` so pending stages are re-evaluated right away.

- Q: Is child-node generation evidence possible inside an engine-level E2E test?
  - A: Yes. `executeWorkflowStageAction(..., actionType: "create_child_nodes_from_plan_yaml")` can be invoked during the scenario to materialize real child nodes from plan YAML.

- Q: How should “AI checks” be represented in current workflow engine behavior?
  - A: Via `expected_results` checks on waiting-input stages, with failure surfacing through `workflow.stage.runtime_input.required` feedback and subsequent pass after remediation.

- Q: Are schema changes needed for this implementation?
  - A: No. Existing workflow events and check-results tables support these behaviors.
