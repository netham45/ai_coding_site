# Task Summary

## Goal and outcome
- Goal: Ensure a plan-created sub-plan can also be auto-extracted, auto-approved, and queued through the same orchestrator flow, while adding deterministic safety checks for recursion, duplicate orchestration, and invalid dependency/topology wiring.
- Outcome: Added approval-time recursion/topology guardrails and stricter revision-level dedupe semantics, plus integration coverage proving recursive sub-plan orchestration works and remains duplicate-safe.

## Key code changes
- `server/src/application/cliServices.ts`
  - Added `MAX_SUB_PLAN_RECURSION_DEPTH = 6`.
  - Added `resolvePlanDepth(...)` helper to compute plan nesting depth and detect cyclic parent-plan relationships.
  - Hardened `approvePlan(...)` duplicate detection to dedupe by `source_plan_revision_id` (global to the approved revision), not just `(source_plan_revision_id, parent_plan_task_id)`.
  - Added recursion-depth validation for sub-plan items during approval; throws `VALIDATION` if depth exceeds limit.
  - Added dependency topology validation so dependencies are rejected when they cross:
    - different `parent_plan_task_id` values, or
    - different merge targets (`sourcePath`/`sourceBranch`).
  - Updated approved-task return queries to use `source_plan_revision_id` for deterministic revision-scoped responses.

- `server/src/integration.test.ts`
  - Added test: `plan-created sub-plans are recursively orchestrated with duplicate-safe approvals`.
    - Verifies parent plan auto-approves a sub-plan item.
    - Verifies that sub-plan can then auto-extract/auto-approve its own items.
    - Verifies repeated orchestration passes do not duplicate child items.
  - Added test: `approvePlan rejects sub-plan recursion beyond depth limit`.
  - Added test: `approvePlan rejects dependencies that cross merge topology boundaries`.

## Tests/validation performed
- From `/server`:

- Final test result: `22/22` tests passed, `0` failures.

## Remaining risks or follow-ups
- Recursion depth limit is currently a hardcoded constant (`6`); making this configurable per deployment may be useful.
- Topology guardrails currently validate merge-target compatibility via source path/branch equivalence; future work could encode explicit topology IDs for clearer diagnostics/analytics.
- Plan orchestration still only triggers when `.ai-plan/latest-plan.yaml` exists; no fallback auto-approval path from raw session output was added.
- Additional orchestration telemetry (depth distribution, guardrail hit rates, pass latency) would improve operability.
