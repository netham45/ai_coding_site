# Task Summary

## Goal and outcome
Goal: Add an `In Progress` button on the task item page that can move a task from any state to `waiting_input`.
Outcome: Implemented end-to-end. The UI now exposes an `In Progress` action (plan + execution task views), and the backend now supports forcing status to `waiting_input` through a dedicated endpoint.

## Key code changes
- Backend route added in `server/src/routes/tasks.ts`:
  - `POST /api/tasks/:taskId/in-progress`
  - Behavior:
    - Returns `404` if task is missing.
    - No-op success if already `waiting_input`.
    - Otherwise transitions task to `waiting_input` using `setTaskStatus(..., "waiting_input", "user_marked_in_progress", ...)`.
    - Emits event `task.mark_in_progress` with `fromStatus` and `toStatus`.
- Backend status helper updated in `server/src/routes/tasks.ts`:
  - `setTaskStatus` now clears `cancel_reason` when transitioning to non-cancelled states (including `merged` and all other statuses handled there), so forced transitions from `cancelled` do not retain stale cancel metadata.
- Frontend updates in `web/src/pages/TaskDetailPage.tsx`:
  - Added `markingInProgress` loading state.
  - Added `markInProgress()` action calling `POST /api/tasks/:id/in-progress`.
  - Refreshes task and project context after success.
  - Added `In Progress` button to both plan-mode and execution-mode action bars.
  - Added success/error toast messaging for this action.

## Remaining risks or follow-ups
- Forced transition from terminal states (`merged`, `failed`, `cancelled`) is now allowed by design for this endpoint; confirm this is desired long-term behavior for audit/workflow policy.
- This action updates task state but does not automatically start runtime; if expected behavior is “set to waiting for user input + runtime attach/start,” that should be explicitly added.
- No dedicated automated test coverage was added for the new endpoint/UI action; consider adding route-level and UI interaction tests.
Goal: Implement the app-vs-project SQLite ownership split defined in `docs/adr-sqlite-persistence-split.md`.
Outcome: Completed. Global entities are persisted in `data/app.sqlite`; project-local entities are persisted in `<project.base_path>/.ai-coding/project.sqlite`.

- Rewired routes/services/websocket gateways to enforce app DB vs project DB ownership boundaries.
