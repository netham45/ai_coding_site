# Task Summary

## Goal and outcome
- Goal: update project lifecycle so creation writes app DB first, then creates `<project.base_path>/.ai-coding/`, initializes/migrates project DB, and seeds project config defaults; also enforce fail-closed load behavior for missing/corrupt project DBs with explicit error codes.
- Outcome: completed. Project creation now performs explicit project DB directory creation and first-time initialization with seeded config defaults, while non-initialization reads/writes fail closed with structured `PROJECT_DB_UNAVAILABLE` / `PROJECT_DB_CORRUPT` errors.

## Key code changes
- Updated `server/src/db/projectDb.ts`:
  - Added typed project DB errors:
    - `ProjectDbErrorCode = "PROJECT_DB_UNAVAILABLE" | "PROJECT_DB_CORRUPT"`
    - `ProjectDbError` and `isProjectDbError(...)`.
  - Added strict initialization controls to `ensureProjectDb(...)`:
    - `initializeIfMissing?: boolean`
    - `configDefaults?: ...` for first-time config seeding.
  - Changed behavior so missing DB is only created when `initializeIfMissing: true`; otherwise throws `PROJECT_DB_UNAVAILABLE`.
  - Converted metadata/config validation failures into `PROJECT_DB_CORRUPT`.
  - `getProjectDb(...)` now calls `ensureProjectDb(..., initializeIfMissing: false)` to prevent implicit DB creation on load paths.
- Updated `server/src/db/index.ts`:
  - Re-exported `ProjectDbError` and `isProjectDbError`.
- Updated `server/src/routes/projects.ts`:
  - Added `respondProjectDbError(...)` helper to map project DB failures into explicit API responses with `code`.
  - Removed silent fallback in project config hydration for ready projects; config read failures now surface as explicit errors.
  - In create flow after clone:
    - explicitly creates `<base_path>/.ai-coding/`
    - calls `ensureProjectDb({ initializeIfMissing: true, configDefaults: ... })` to initialize/migrate and seed defaults.
  - Wrapped project-loading paths (`list`, `get`, `files`, `patch`, and project IDE routes) to fail closed on project DB unavailability/corruption.

## Tests/validation performed
- Ran `npm run build -w server`.
- Result: successful TypeScript compile with no errors.

## Remaining risks or follow-ups
- API clients currently extract only `error` text; they may need to consume/display the new `code` field consistently.
- Other project-scoped routes/services (outside `projects.ts`) should be audited to ensure they also map `ProjectDbError` codes consistently where applicable.
- No dedicated automated tests were added yet for:
  - missing project DB on non-initialization read paths,
  - metadata mismatch/schema drift,
  - corrupt/unopenable SQLite file behavior.
