## Goal and outcome
- Goal: Add built-in workflows for `epoch` / `phase` / `plan` nodes so they run through the workflow engine instead of legacy direct orchestration patterns, with stage-level handling for plan YAML generation, child-node ingestion, and child-completion gating.
- Outcome: Implemented built-in workflow definitions and start wiring across CLI/API/queue paths for non-exec tiers, added workflow-engine stage-rule gating for child generation and completion, and implemented concrete `create_child_nodes_from_plan_yaml` stage action behavior that reads `.ai-plan/latest-plan.yaml`, validates, persists children/dependencies, and records workflow artifacts.

## Key code changes
- Added built-in workflow service:
  - `server/src/services/workflowBuiltins.ts`
  - Introduces built-in workflow definition provisioning (`builtin.<tier>.workflow`) and idempotent run startup per task for `epoch|phase|plan`.
  - Built-in stages:
    - `generate_plan_yaml`
    - `ingest_child_nodes` (depends on `generate_plan_yaml`)
    - `wait_for_child_completion` (depends on `ingest_child_nodes`)

- Wired node starts to workflow engine for non-exec tiers:
  - `server/src/application/cliServices.ts`
    - `startNode` now starts workflow runs for `epoch|phase|plan` via `startBuiltinWorkflowForTierTask(...)`.
    - Retains runtime session start for `exec` tier.
    - Emits `orchestration.manual_start` with strategy `workflow_engine` for workflow-based starts.
  - `server/src/routes/tasks.ts`
    - `POST /nodes/:nodeId/start` now mirrors same behavior as CLI path.
  - `server/src/services/queue.ts`
    - Queue dispatcher now resolves node tier and routes `epoch|phase|plan` to workflow start, `exec` to runtime start.

- Added workflow stage-rule gating in engine:
  - `server/src/services/workflowEngine.ts`
  - New rule checks on pending stages:
    - `ingest_child_nodes` blocked until `.ai-plan/latest-plan.yaml` exists and is non-empty for workflow task workspace.
    - `wait_for_child_completion` blocked while any child task (`parent_plan_task_id = parent`) is not `merged`.
  - Blocked lifecycle events include unresolved stage-rule details.

- Replaced placeholder child-ingestion stage action with real implementation:
  - `server/src/services/workflowStageActions.ts`
  - `create_child_nodes_from_plan_yaml` now:
    - Resolves parent task context from `workflow_runs.task_id` (or `actionInput.parentTaskId`).
    - Reads YAML from `.ai-plan/latest-plan.yaml` (or `actionInput.planPath`).
    - Parses with existing `parsePlanYaml(...)`.
    - Validates dependencies/cycles with `validateProposedNodeGraph(...)`.
    - Creates child tasks + task state transition rows + `task_dependencies` in one DB transaction.
    - Emits `workflow.stage.action.child_nodes_created` artifact event.
  - `review_child_nodes` default now can load children from DB if not provided in input and reports both failing and incomplete counts.

- Added/updated tests:
  - Added: `server/src/services/workflowBuiltins.test.ts`
    - Verifies built-in run creation and idempotent reuse for plan-tier task.
  - Updated: `server/src/services/workflowEngine.test.ts`
    - Added stage-rule gating coverage for ingest/wait stages.
  - Updated: `server/src/services/workflowStageActions.test.ts`
    - Added coverage for reading `.ai-plan/latest-plan.yaml`, creating children/dependencies, and artifact event emission.

- No built-in workflow definition provisioning existed for node tiers.

- Existing parser/graph utilities were sufficient to implement robust ingestion without schema changes.

## Questions answered during this task, including each answer
- Q: Are epoch/phase/plan nodes already started through workflow runs?
  - A: No. They were still being started via runtime sessions in CLI/API and queue paths.

- Q: Is there already a built-in workflow definition registry for node tiers?
  - A: No. Added a built-in definition/service layer to provision and reuse workflows by tier.

- Q: Should child-ingestion stage action rely on inline YAML payload?
  - A: No for default behavior. It now reads `.ai-plan/latest-plan.yaml` from the parent task workspace.

- Q: How should child completion gating be enforced in workflow progression?
  - A: Via workflow engine stage rules on `wait_for_child_completion`, blocking until all child tasks are `merged`.

- Q: Can dependency/cycle validation be implemented without new schema?
  - A: Yes. Reused `validateProposedNodeGraph(...)` and existing task/dependency tables.

## Remaining risks or follow-ups
- Workflow stage actions are implemented at service level; higher-level automation loops that should invoke `executeWorkflowStageAction(...)` on running stage runs still need explicit orchestration wiring if not already handled elsewhere.
- `generate_plan_yaml` stage is represented as a built-in stage in definitions, but a concrete default action runner for generating YAML from runtime output is not yet wired in this task.
- Child task creation path in workflow stage action currently persists DB rows/dependencies and metadata but does not perform full git workspace initialization/branch setup used by `approvePlan(...)`; if required for immediate execution, that should be aligned.
- Existing integration tests focused on legacy/previous orchestration paths may need expansion to assert end-to-end built-in workflow execution across epoch/phase/plan in runtime worker contexts.
