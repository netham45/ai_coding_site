# Task Summary

## Goal and outcome
- Goal: implement an idempotent migration routine that iterates projects in app DB, creates/migrates each project DB, copies project-owned data/config into project DB, verifies migration integrity, records status, and only removes app-owned legacy data after verification.
- Outcome: completed. A startup backfill routine now migrates project-scoped entities and legacy prompt/config fields into per-project DBs, tracks per-project migration status, verifies row counts (and optional checksums), and supports gated post-verification cleanup.

## Key code changes
- Added `server/src/db/projectDataMigration.ts` with a full backfill/verification pipeline:
  - Added `project_data_migrations` table management with statuses: `in_progress`, `verified`, `cleaned`, `failed` plus attempt count, timestamps, counts/checksum JSON, and last error.
  - Added legacy table/column detection so migration logic is resilient to partially migrated app DB schemas.
  - Implemented per-project copy/upsert from app DB to project DB for:
    - `tasks`
    - `task_dependencies`
    - `task_state_transitions`
    - `task_sessions`
    - `plan_revisions`
    - `plan_revision_items`
    - `plan_revision_item_dependencies`
    - `ide_instances`
    - `merge_records`
    - `events`
  - Added legacy prompt/config copy from app `projects` columns into project DB `project_config` via `upsertProjectConfig(...)` when legacy columns exist.
  - Added verification of source vs target row counts per migrated entity, plus optional SHA-256 checksums.
  - Added cleanup path (only after successful verification) to remove migrated project-scoped rows from app DB and clear legacy config columns.
  - Added cleanup verification to ensure app-side migrated rows are actually removed.
  - Added dynamic event-scope SQL generation to handle presence/absence of legacy task/session tables safely.
- Updated `server/src/db/appDb.ts`:
  - App DB initialization now calls `runProjectDataMigrationBackfill(db)` after baseline/legacy migrations.

## Tests/validation performed
- Ran `npm run build -w server` after implementation.
- Result: TypeScript compilation succeeded with no errors.

## Remaining risks or follow-ups
- Operationally, cleanup is disabled by default and requires `PROJECT_DATA_MIGRATION_CLEANUP_LEGACY=1`; teams should run verification-only first, inspect `project_data_migrations`, then enable cleanup.
- Optional checksum verification is also gated by `PROJECT_DATA_MIGRATION_VERIFY_CHECKSUMS=1`; enabling it may be slower on large datasets.
- The wider app still has routes/services that read/write task/runtime data via app DB in places; those paths still need full cutover to project DB handles for complete ownership consistency.
- No dedicated automated tests were added for this migration routine yet (idempotency retry behavior, checksum mismatch handling, cleanup safeguards, mixed-schema detection).
