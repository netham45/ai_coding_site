## Goal and outcome
- Goal: Add orchestration API surfaces for full hierarchy navigation, start-from-any-tier control, blocked diagnostics, dependency graph visibility, replan counters, and manual override operations, while keeping existing `/api/tasks` and `/api/plans` consumers compatible.
- Outcome: Added new node/project orchestration endpoints and action routes, expanded task/plan payloads with orchestration control and replan state, introduced orchestration contract schemas, and added integration coverage for hierarchy/graph and override action auditing. Existing task/plan endpoints remain intact and backward compatible.

## Key code changes
- Added orchestration read/action endpoints in `server/src/routes/tasks.ts`:
  - Read:
    - `GET /api/projects/:projectId/hierarchy`
    - `GET /api/projects/:projectId/dependency-graph`
    - `GET /api/nodes/:nodeId`
  - Actions:
    - `POST /api/nodes/:nodeId/start`
    - `POST /api/nodes/:nodeId/auto-mode`
    - `POST /api/nodes/:nodeId/auto-merge`
    - `POST /api/nodes/:nodeId/force-re-review`
    - `POST /api/nodes/:nodeId/approve-budget-override`
- Expanded node serialization in both routes/services to include orchestration controls and replan counters:
  - `orchestrationControls.autoMode`
  - `orchestrationControls.replan.{maxIterations,iterationsUsed,remainingIterations,budgetOverride,gapHashesSeen}`
- Expanded `server/src/routes/plans.ts` plan detail response to include dependency diagnostics and matching orchestration/replan serialization fields.
- Added service-level orchestration actions in `server/src/application/cliServices.ts`:
  - `startNode`
  - `toggleNodeAutoMode`
  - `toggleNodeAutoMerge`
  - `forceNodeReReview`
  - `approveNodeBudgetOverride`
- Added API contract schemas in `server/src/api/contracts/orchestration.ts` for orchestration-related inputs and graph/control response shapes.
- Added integration tests in `server/src/integration.test.ts` for:
  - hierarchy + dependency graph payload completeness across epoch->phase->plan->task->exec
  - manual override action validation and audit-event recording

## Remaining risks or follow-ups
- New orchestration action endpoints are implemented at HTTP route + service layer, but CLI command wiring for explicit user-facing subcommands was not added in this task; if required, add command parser bindings in `server/src/cli/index.ts`.
- Hierarchy currently derives parent/child structure from `parent_plan_task_id` and task rows; if future tiers gain non-task persistence models, hierarchy construction should be generalized.
- Replan/override state is metadata-driven; downstream UI/analytics consumers should verify they read from the new `orchestrationControls` payloads consistently.
- Dependency graph endpoint reports task-backed nodes and metadata dependencies; if strict referential checks are later required for non-task tiers, additional persistence/lookup guarantees will be needed.
