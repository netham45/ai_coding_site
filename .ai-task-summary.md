## Goal and outcome
- Goal: Add a migration/backfill that attaches the correct default workflow context to existing nodes (tasks), while preserving status and avoiding disruption of active runs.
- Outcome: Implemented a transactional, idempotent workflow backfill service and wired it into DB initialization/migration paths. Existing tasks now gain workflow runs safely when missing; tasks/runs that already have workflow context are skipped.

## Key code changes
- Added backfill service:
  - `server/src/services/workflowBackfill.ts`
  - New function: `backfillDefaultWorkflowsForExistingTasks(...)`.
  - Behavior:
    - Scans existing tasks.
    - Infers tier from `metadata_json` when present, with deterministic fallback (`mode`, `source_plan_revision_id`).
    - Attaches built-in workflow definitions for `epoch|phase|plan` tasks.
    - Attaches default exec workflow for `task|exec` tasks.
    - Creates missing workflow runs only (skips tasks that already have any run).
    - Maps task terminal statuses to workflow terminal statuses:
      - `merged -> succeeded`
      - `cancelled -> cancelled`
      - `failed|merge_conflict -> failed`
      - others -> `queued`
    - For terminal mappings, backfills `started_at/completed_at/updated_at` to task `updated_at`.
    - Wraps backfill in a DB transaction for rollback safety.

- Exposed reusable definition-ensure helpers:
  - `server/src/services/defaultExecWorkflow.ts`
    - Exported `DEFAULT_EXEC_WORKFLOW` constants.
    - Exported `ensureDefaultExecWorkflowDefinition(...)`.
  - `server/src/services/workflowBuiltins.ts`
    - Exported `builtinWorkflowNameForTier(...)`.
    - Exported `ensureBuiltinWorkflowDefinitionForTier(...)`.

- Wired backfill into migration/initialization:
  - `server/src/db/projectDb.ts`
    - Bumped `PROJECT_DB_SCHEMA_VERSION` from `3` to `4`.
    - Added `upgradeProjectDbToV4(...)` that runs workflow backfill.
    - Added `user_version < 4` migration step and sets `user_version = 4`.
  - `server/src/db/appDb.ts`
    - Runs workflow backfill during app DB initialization after legacy schema migration setup.

- Updated integration schema expectations:
  - `server/src/integration.test.ts`
    - Updated expected migrated `user_version` and metadata schema version from `3` to `4` where asserted.

- Added tests:
  - `server/src/services/workflowBackfill.test.ts`
    - Verifies backfill attaches correct workflow definitions/runs.
    - Verifies idempotency (second run creates nothing new).
    - Verifies rollback safety (forced insert failure causes full transaction rollback).

## Questions answered during this task, including each answer
- Q: How should we choose workflow type for existing tasks?
  - A: Use node tier inference. `epoch|phase|plan` get built-in tier workflows; `task|exec` get default exec workflow.

- Q: Should backfill start or auto-progress newly attached runs?
  - A: No. Backfill only attaches missing workflow context and preserves current execution behavior by creating queued/terminal-aligned runs without starting active processing.

- Q: How do we preserve status without breaking active runs?
  - A: Do not modify tasks; skip tasks that already have a workflow run; map only terminal task statuses to terminal workflow statuses for newly attached runs.

- Q: How is idempotency guaranteed?
  - A: Backfill checks for any existing `workflow_runs` row by `task_id` and skips if present. Re-running the backfill creates no duplicates.

- Q: How is rollback-awareness handled?
  - A: Entire backfill pass is wrapped in a DB transaction. Any failure rolls back both definitions and run inserts from that pass.

## Remaining risks or follow-ups
- Current backfill skip rule is coarse (`skip if any run exists for task`). This is safest for preservation, but it does not reconcile tasks whose existing run uses a non-default definition.
- Backfilled non-terminal runs default to `queued`; if stronger historical status parity is needed for in-progress tasks, a future mapping policy may be added.
- App DB startup now runs backfill as part of init; for very large legacy datasets, performance monitoring and optional batching/observability may be useful.
- If future workflow versions are introduced, a separate version-upgrade migration strategy for existing runs/definitions may be needed.
